SQL从读懂到能写：四个核心积木

0. 一张表到底是什么

把表看成Excel。一列是字段，一行是一次观察。最先问“这一行是什么”。customers每行一个客户；loan_applications每行一次申请；loans每行一笔借款；repayments每行一期应还和汇总支付。一个客户可以多次申请，一笔贷款可以分很多期，所以这些表不能随意拼起来求和。

记住一句话：先确定最终一行代表什么，再决定如何汇总和连接。

1. SELECT、WHERE和CASE WHEN

SELECT application_id, customer_id,
       CASE WHEN approval_status='Approved' THEN 1 ELSE 0 END AS approved_flag
FROM loan_applications
WHERE requested_amount >= 100000;

逐行翻译：FROM选择申请表；WHERE只留下申请金额至少10万的记录；SELECT选出要看的列；CASE给每行做判断，通过写1、否则0；AS给新列命名。此处10万只是筛选练习，不是推荐准入阈值。

CASE像Excel的IF，但能写多层。条件按先后顺序匹配，命中一项后不再继续。分数600应进入600–699，所以第一项写 <600，第二项写 <700。不要在两项都写包含600的闭区间然后忽略顺序。

NULL是未知，不是0，也不是空字符串。用 IS NULL，不要写 = NULL。COALESCE(x,0)是在明确“缺失应当按0处理”时才用，不能把缺失信用分改成0后声称他高风险。

2. GROUP BY：把很多行压成每组一行

小表：A支行两笔金额100和200，B支行一笔300。

SELECT branch_id, COUNT(*) AS loan_count, SUM(loan_amount) AS total_amount
FROM loans
GROUP BY branch_id;

结果只有两行：A→2笔/300，B→1笔/300。原来具体哪笔贷款金额100的信息不在这个结果里了。

COUNT(*)数行，包括某些列为空的行；COUNT(paid_date)只数非空日期。COUNT(DISTINCT customer_id)数不同客户，不能拿来替代贷款数。SUM求总额，AVG求平均。整数除法可能截断，比例用100.0或1.0确保小数运算。

WHERE在分组前筛原始行，HAVING在分组后筛整组：

SELECT customer_id, COUNT(*) AS n
FROM loans
WHERE status <> 'closed'
GROUP BY customer_id
HAVING COUNT(*) >= 2;

这问的是“至少两笔未结清贷款的客户”，与Q15“历史至少两笔贷款”不同。面试中改一个WHERE就换了业务口径。

3. CASE加聚合：一张表里同时算多个指标

SELECT COUNT(*) AS applications,
       SUM(CASE WHEN approval_status='Approved' THEN 1 ELSE 0 END) AS approved,
       100.0 * SUM(CASE WHEN approval_status='Approved' THEN 1 ELSE 0 END)
       / NULLIF(COUNT(*),0) AS approval_rate_pct
FROM loan_applications;

CASE先给每行打0/1，SUM再数有几个1。NULLIF(x,0)把0分母改成NULL，避免除零。7500次申请6112次通过，率为81.4933…%，四舍五入81.49%。如果先WHERE Approved，分母也只剩通过申请，结果将永远100%。这是面试最常见的陷阱之一。

平均比例的陷阱：甲组1/2=50%，乙组9/10=90%，总率是10/12=83.33%，不是两个率平均得到70%。先加分子与分母，再相除。

4. JOIN：按键把字段接过来

SELECT l.loan_id, l.loan_amount, c.credit_score
FROM loans l
LEFT JOIN customers c ON l.customer_id=c.customer_id;

l、c是别名，让表达简洁。ON规定配对方式。客户表customer_id唯一时，这是多对一：许多贷款对应一个客户，连接后应仍是6112行。

INNER JOIN只保留匹配上的。LEFT JOIN保留全部左表，右表找不到时填NULL。若LEFT JOIN之后在WHERE写 c.credit_score>=600，没有客户匹配的NULL行也会被滤掉。想保留左表且仅接符合条件右表，把条件放ON并单独标记缺失；想只看分数达标贷款，WHERE才是目标。不能死记“所有条件都放ON”。

为什么本金会凭空变多

贷款L1本金100，有两期还款30、40。直接JOIN后变两行：(L1,100,30)、(L1,100,40)。SUM本金成200，而真实本金还是100。

WITH paid AS (
  SELECT loan_id, SUM(amount_paid) AS total_paid
  FROM repayments GROUP BY loan_id
)
SELECT l.loan_id, l.loan_amount, COALESCE(p.total_paid,0) AS total_paid
FROM loans l LEFT JOIN paid p ON l.loan_id=p.loan_id;

先把分期压成每笔贷款一行，再JOIN。SUM(DISTINCT loan_amount)不是修复：两笔不同贷款本金都是100，DISTINCT会错误只算一次。正确去重单位是业务主键，不是金额。

面试写完JOIN立刻口述三项检查：右表键是否唯一；连接前后主表行数是否改变；关键金额是否对账。

5. 窗口函数：保留明细，额外挂上组内计算结果

仍用100、200、300的三行小表：

SELECT loan_id, branch_id, loan_amount,
       SUM(loan_amount) OVER(PARTITION BY branch_id) AS branch_total
FROM loans;

结果仍三行。A的两行分别是100/组总300、200/组总300，B是300/组总300。GROUP BY像“收起明细只看汇总”；窗口像“保留每张账单，在旁边写所属支行汇总”。

面试60秒：GROUP BY和窗口的区别

GROUP BY通常将每组压成一行，适合支行总额、分组违约率。窗口函数在保留当前结果粒度的同时进行分区计算，适合组内排名、累计值、上一期值。窗口不是更高级的GROUP BY，两者常配合：先按月聚合，再对月度结果做累计。窗口也能用于已经GROUP BY过的结果，保留的是该阶段的行数。

OVER里的三个组成部分

- PARTITION BY：各算各的。例如按客户分开排名。省略时整个结果一个区。

- ORDER BY：计算顺序，例如申请日期倒序；它不保证最终展示顺序，外层仍需ORDER BY。

- ROWS/RANGE：当前行计算时能看哪些邻居。累计用ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW，即从开头到当前。

三个排名函数

金额100、100、80倒序。ROW_NUMBER得到1、2、3；RANK得到1、1、3；DENSE_RANK得到1、1、2。取恰好3条用ROW_NUMBER加稳定排序键；取前三种不同金额用DENSE_RANK，可能超过3行。

每客户最新申请

WITH ranked AS (
 SELECT application_id,customer_id,application_date,
        ROW_NUMBER() OVER(
          PARTITION BY customer_id
          ORDER BY application_date DESC, application_id DESC
        ) AS rn
 FROM loan_applications
)
SELECT * FROM ranked WHERE rn=1;

先每位客户单独排队，再挑第一条。为什么不能本层WHERE rn=1？按SQL逻辑处理顺序，本层WHERE发生在窗口求值之前，所以需要CTE/子查询外包一层。为什么多排application_id？同日多次申请需要明确谁在前，避免每次结果不稳定。

LAG(x)取排序后前一行的值，首行没有前项得到NULL。不是自动找前一个自然日；若缺日期，前一行可能是三天前。累计、滚动与环比都必须先检查时间连续性。

6. 7行不等于7天

若只在1号、3号、10号有订单，ROWS BETWEEN 6 PRECEDING AND CURRENT ROW表示最多7条已有记录，不是近7个自然日。解决方案：先生成每日日期序列并补零，再用7行窗口；或者使用数据库支持的时间RANGE。本文I03用补日历方式，跨数据库更容易解释。今天是否纳入、退款如何处理、支付时间还是创建时间，先问清再写。

pandas：把SQL思路搬进Python

DataFrame就是内存里一张带列名的表，Series通常是一列。先理解每一步输入和输出是什么，再背函数。运行pandas_lab.py可查看八题真实输出；pandas_exercises.py留给你自己填写，不要直接复制答案。

P01 筛选：先做“每行是否留下”的布尔列

目标：申请通过、金额至少10万，输出申请ID、客户ID和申请金额，按申请ID排。

a = d['loan_applications']
mask = (a['approval_status'] == 'Approved') & (a['requested_amount'] >= 100000)
out = a.loc[mask, ['application_id','customer_id','requested_amount']]
out = out.sort_values('application_id').reset_index(drop=True)

a['approval_status']=='Approved'得到一串True/False，不是一个真假值。&逐行做“且”，|逐行做“或”，~做“非”。Python的and/or用于单个真假判断，不能直接替代Series的&/|。两边要加括号，避免运算优先级出错。loc[行条件,列清单]同时控制留下哪些行和列。reset_index只重置显示索引，不是改申请ID。

练习变式：把“且”换成“或”，先猜行数变大还是变小。自检：所有输出行通过且>=100000，列只有三列，原表未被改动。

P02 分组：agg汇总成每支行一行

a = d['loan_applications'].copy()
a['approved_flag'] = a['approval_status'].eq('Approved').astype(int)
out = a.groupby('branch_id',as_index=False).agg(
    applications=('application_id','size'),
    approved=('approved_flag','sum')
)
out['approval_rate_pct'] = 100*out['approved']/out['applications']

copy是为了不意外改动外部共用表。eq相当于==，astype(int)把True/False变1/0。agg里的“新列名=(旧列名,函数)”叫命名聚合。as_index=False让branch_id仍是普通列，后面merge更方便。

size数行，count数非空，区别对应COUNT(*)与COUNT(字段)。缺失支行要保留时写dropna=False。不要把支行通过率直接平均得到全局通过率，应加总通过数再除总申请数。

P07 pivot和pivot_table：行列交叉汇总

                            values='loan_amount',aggfunc='sum',fill_value=0)

A01 三数之和

题意：给整数列表，找所有不重复的三元组，使三数之和=0。不同下标可取相同值，结果按数值去重，不能反复用同一下标。例[-1,0,1,2,-1,-4]输出[-1,-1,2]与[-1,0,1]。

最笨方案三重循环O(n³)，适合用来校验小样本。优化：排序后固定第一个数，剩下两个用左右指针。和小于0就左指针右移，让和变大；和大于0就右指针左移，让和变小；找到0则记录，两侧移动并跳过相同值。

手走：排序[-4,-1,-1,0,1,2]。固定-4，最右两数1+2也只到-1，没有解。固定第一个-1，left=-1、right=2，和0记录；随后left=0、right=1又得0。固定第二个-1会重复，所以跳过。

完整可执行版本在algorithms.py的three_sum。逐句自检：为什么i只到n-3？因为后面至少留两位；为什么left<right？禁止重复下标；为什么跳过重复i？结果去重；为什么找到解后两边都移动？相同i下原来的两个值组合已处理。

排序O(n log n)，固定每个i后双指针最多走O(n)，总时间O(n²)。本实现sorted创建副本O(n)，结果集合空间另计。边界：空数组、长度不足3、[0,0,0,0]只输出一个[0,0,0]、全正、全负。测试用暴力枚举与优化解交叉校验。

A02 快速排序

先学容易解释的三路版本：挑pivot，把数分为小于、等于、大于三份，左右递归排序，再拼起来。基例len<=1直接返回。比如[3,1,2,3,0]挑2，得到[1,0]、[2]、[3,3]，分别处理后拼成[0,1,2,3,3]。

本包quick_sort是易读的非原地版本。平均时间O(n log n)，极端不平衡最坏O(n²)。选择中间下标的元素不等于选中位数，仍可能遇到坏情况。大量重复时equal组一次带走很有帮助。

因为创建新列表，本实现不要声称额外空间O(log n)：均衡时峰值约O(n)，极端递归分割可能达到O(n²)并触发递归深度限制。原地分区版本只需交换数组元素，但平均递归栈O(log n)、最坏O(n)。面试若要求原地，请先确认，然后解释双指针分区，而不是拿这个版本冒充原地。

与归并排序区别：快排围绕pivot分区，最坏可退化；归并通常稳定O(n log n)，数组实现常用O(n)辅助空间。实际Python业务常用sorted，自己手写是算法考查。

3. 精准率、召回率、误伤率

约定“坏客户=正类1，标记高风险=预测正类”。100个客户里20个后来违约，策略标了15人，其中12人后来违约，3人没违约。于是TP=12，FP=3，FN=8，TN=77。

- Precision精准率=TP/(TP+FP)=12/15=80%：标出来的有多少真坏。审核资源有限时关心命中效率。

- Recall召回率=TP/(TP+FN)=12/20=60%：全部坏客户中抓到了多少。漏掉风险多时关心它。

- FPR假阳性率=FP/(FP+TN)=3/80=3.75%：全部好客户中误标多少。

- 1-Precision=3/15=20%：被标人群中误标占比，与FPR分母不同。面经说“误差率/误杀率”时必须先定义。

- Accuracy准确率=(TP+TN)/全部=89%。若只有1%坏，全部预测好也有99%准确率，因此不能只看它。

真实违约标签通常有延迟，今天刚放款的客户不能标成“好”。申请后只观测到已经放款的人，拒绝者缺少“如果放款会怎样”的结果，存在选择偏差。借据冻结期间也不代表好坏已确定。

追问：高使用率一定差吗？不一定，有人正常集中消费后全额还清。与延期次数、近期支付变化一起判断。性别、年龄等即使相关也不能直接当可用业务决策依据，需合规、合理性和公平性审查。本包不将这些人口属性用于模型，但这仍不能证明模型公平。

问2：衍生特征有哪些，为什么时间交叉往往有帮助

计数（近3月延期几次）；金额统计（均值、最大、波动）；比例（账单/额度）；趋势（最近3月与前3月差异）；距离上次事件的时间；序列（连续延期月数）；交叉（高使用率且近期延期）。

时间有时有效，因为一次异常可能偶然，持续/加速恶化更能反映状态；不同窗口区分短期波动与长期习惯。例如半年都稳定、最近突然高负债，和半年一直高负债可能不同。但窗口并非越多越好，容易共线、过拟合或泄露未来。必须所有特征在决策当时已经可用。统计窗口截止日与数据入库时间都要控制。

本包真实数据只有一个半年历史窗口，不能验证跨年份稳定。不能把同一客户2005年9月的标签反向用于4月特征。

问3：如何提高授信率，如何提高回收率

先说你没有真实上线case，不编造提升业绩。给一个“假设方案”：发现某规则拒绝很多低风险边缘客户→核对拒绝原因与数据缺失→仅对一类可验证收入且历史履约稳定的客户放宽阈值/补充验证→控制额度与总敞口→用成熟标签回测并评估收入与损失→灰度对照并设止损。不能通过重复计数申请或换分母做高通过率。

回收率：首先定义现金回收/到期应收还是违约后回收/EAD。排除未到期分母和重复流水。按逾期阶段、联系可达性、还款能力分层，测试提醒时点与渠道、便捷还款、困难客户的合规分期/协商。比较扣除成本后的增量回收，而非只看总额。严禁暗示骚扰、威胁或绕过合规可以提高回收。

问4：接触哪些模型，分区间的风险分层有什么意义

诚实答“本次实操用了逻辑回归，理解树模型原理，但没声称训练过所有模型”。分数分层把连续排序变成可行动的客群，例如低风险正常服务、中风险补充验证、高风险人工复核。各档看样本量、坏账率、召回、覆盖量、稳定性和公平性，帮助选阈值与配置审核资源。

风险随分数大体单调是有用信号，但不强求每档严格单调：小样本会抖动。需要置信区间、账龄一致、时间外验证。不要只凭某档坏账率0就认定无风险。

问5：评分卡与XGBoost的变量筛选逻辑有什么不同

典型评分卡常用分箱、WOE转换和逻辑回归，重视可解释性、单调性、稳定性、共线性及业务合理性。IV可做单变量初筛，但不是唯一标准。XGBoost可学习非线性和变量交互，分裂按目标损失改进寻找特征，常结合验证集、置换重要性、SHAP、稳定性、消融等筛选。

不能说“评分卡只看IV、XGBoost只看gain”。高IV可能来自泄露；gain可能偏向可分裂点多的变量；强相关变量可能相互分摊贡献。两者都要排除未来信息、检查缺失和漂移、控制复杂度，并在未用于选择的数据上检验。

WOE一个常见约定是ln(good_bin_share/bad_bin_share)。good_bin_share指这档好客户/全部好客户，bad同理；不是这档内部好坏占比。IV=各档(good_share-bad_share)×WOE之和。某档为0需合并或平滑，且仅在训练集拟合分箱。方向约定不同可导致WOE正负相反，应说明自己的约定。本项目没有完成评分卡分箱，不把概念答题说成实际产出。

问6：LightGBM迭代原理，与随机森林区别

随机森林像多位相对独立的评委：对样本和特征引入随机性，分别训练树，最后平均概率或投票，主要降低方差。Boosting像后续评委专门修正当前整体错误：第t轮加一棵树，根据损失函数的梯度方向改进前面的组合，而非所有树互不相关。

简式F_t(x)=F_{t-1}(x)+ηh_t(x)。x是客户特征，F是当前模型打分，h_t是新树输出，η是学习率控制每次改动幅度。对平方误差，拟合残差很直观；对二分类交叉熵更准确说使用梯度/二阶信息，不能说每轮只是机械拟合0/1残差。

LightGBM使用直方图分桶减少候选切分计算，通常按收益最大的叶子优先生长，训练高效但小样本更需约束叶子数、深度和叶子最小样本量。XGBoost也支持hist，不能背成“只有LightGBM有直方图”。GOSS/EFB属于其相关机制，不要误称所有配置都默认开启。

5. 逻辑回归、AUC、KS、损失函数

逻辑回归先把特征做线性组合z=b+Σw_j x_j，再用sigmoid：p=1/(1+exp(-z))映射到0–1。x_j是第j个客户特征，w_j是系数，b是截距，p是次月违约预测概率。正系数提高风险打分，但特征相关时不能当因果影响。

二分类交叉熵单样本L=-[y ln p +(1-y) ln(1-p)]。y是实际违约0/1，p是预测违约概率。实际违约却预测p接近0，会遭到大惩罚。训练最小化平均损失再加正则约束系数，避免把训练样本记死。sklearn逻辑回归C越小正则越强，与“正则强度λ”方向相反。

AUC可直观理解为随机抽一个坏客户和一个好客户，模型把坏客户风险排更高的概率（并列通常计半次）。它评价排序，不告诉你阈值是否适合当前审核资源，也不保证概率准。KS是各阈值处坏客户累计命中率与好客户累计误标率的最大差。Brier是平均(p-y)²，越小越好，但受总体违约率影响，比较时使用同一批样本。

训练集用来学系数，验证集用来选超参数与阈值，测试集留到选择完成后报告一次。标准化均值与方差只在训练集拟合。不要为了报告好看反复看测试集调特征，随机holdout也不等于能抗时间漂移。

6. 电商面经怎样迁移到信贷

“资损降30%，GMV掉2%”不能仅比较百分比大小。假设原资损100万元，少30%=节省30万元；原GMV1亿元，少2%=少200万元交易，若贡献率10%对应20万元贡献损失，还未算投诉、长期留存与运营成本。这个算例只说明要统一金额口径，不是认为策略一定该上线。

大促也不代表自动允许更多误伤。应由场景风险敞口、利润、合规、体验和风险偏好决定，有硬红线就不能为了GMV突破。信贷类似：放宽策略要结合新增利息/费用、资金与获客成本、预期损失及额度敞口；没有这些数据就给验证计划，不编ROI。

出现异常时：先判断止损红线、保留日志，必要时回滚/缩小灰度；核对指标与数据延迟；按渠道、客群、产品、版本、账龄拆分；识别结构变化还是组内变化；提出补充验证/人工复核等分层处理；重新在对照实验中检验。白名单要有明确条件、审核和到期机制，不能随意放行关系客户。

7. 深挖：没有ground truth，为什么还做模型

ground truth是尽可能可信的真实结果。若标签完全来自规则A，再训练模型去拟合A，验证集也按A打标，只能证明模型复制规则，不能证明识别更多真实风险。模型价值可以是假设中的泛化、组合软信号和发现规则未覆盖样本，但必须独立标签验证。

可用人工抽审、实际损失、申诉复核、后续成熟履约构建有质量等级的标签；同时记录不确定样本。审查只盯模型高分会造成验证偏差，应分层随机抽样并考虑抽样权重。规则标签可用于弱监督，但训练/验证标签依赖要披露。

GCN是利用图中相连节点和邻居信息学习表示的方法。风控里设备、账号、地址等可构图，但同IP不等于黑产，宿舍/企业网络会造成误伤。你没有实操图模型时，说明理解关联风险与独立验证的重要性即可，不必赶在三天内做一个假图模型项目。

8. 自动调整策略如何设计

先定义目标与约束，而不是让模型自由改阈值。比如最大化“预期收入−预期损失−审核成本”，同时满足最大审核量、最大误伤、合规限制和风险红线。输入是有截止日、标签成熟规则的数据；候选参数有允许范围；只在验证窗口评估；经过审批进入小流量，监控红线并自动回滚。

标签延迟时不宜频繁追逐短期好看指标。短期监控通过量、特征缺失、审核负荷、投诉；长期看成熟逾期与损失。自动化不等于撤掉人：保留审计日志、版本、权限和人工复核。你可以把“训练/验证/样本外、时间对齐、成本约束”的量化研究经验迁移过来，但不把资产定价结果当信贷业绩。

9. 项目监控回答模板

五层检查：数据质量（缺失、延迟、重复、分布）；策略执行（命中率、通过率、规则冲突）；业务量（申请、授信、提款、额度使用）；成熟风险（FPD、DPD、Vintage、损失）；体验运营（审核时效、客诉、申诉、回收成本）。趋势异常先与同星期、渠道占比、账龄和活动周期对齐。可用历史分位数或控制图设预警，但阈值必须用历史数据验证，不能凭空说3σ适用于全部指标。

主项目手把手：真实信用卡客户的风险分层

先讲清楚项目一句话

用UCI公开的真实历史信用卡客户记录，比较“只看最近一期”与“加入半年履约频率和趋势”的逻辑回归，在相同留出客户上评估风险排序和模拟复核队列。它是离线复现与改进，不是实际发放贷款或催收实验。

源：Yeh, I. (2009). Default of Credit Card Clients. UCI Machine Learning Repository. DOI:10.24432/C55S3H。官方页面 https://archive.ics.uci.edu/dataset/350/default+of+credit+card+clients 。CC BY 4.0许可，保留出处。文件哈希在real_project/data/source.json。30,000个ID，23个特征，另有ID与标签；不是25个模型特征。

第1步：先认识一行

原表一行一个客户ID。LIMIT_BAL是授信额度，单位新台币。PAY_0是最近一期即2005年9月的还款状态，PAY_2至PAY_6对应8月至4月。BILL_AMT1–6是六个月账单金额，PAY_AMT1–6是对应月份支付金额。目标default payment next month为次月是否违约，1=是、0=否。

不能把LIMIT_BAL直接当实际借款额，也不能把PAY_0的2说成逾期2天。原始账单金额可能为负，可能涉及冲抵等原因；缺少业务解释时保留并报告，不自动删成“异常”。官方字典没有完整解释所有实存还款状态值，特别-2与0，因此当前状态以类别编码保留，历史“延迟月份”只按正数计，解释为源编码下的正向延迟状态。

SEX、AGE、MARRIAGE、EDUCATION不纳入本次模型。ID只做关联与划分，不作为预测变量。排除人口属性不代表模型自动公平，其他特征也可能是代理变量。

第2步：数据质量核验

打开real_project/run_real.py的build函数，先看assert：30,000行、ID唯一、没有空单元格、LIMIT_BAL>0、标签仅0/1、源文件哈希匹配。assert的作用是“假设不成立就停止”，避免一路产出漂亮但错误的图。

这不等于数据完美。教育和婚姻存在字典未完整解释的编码，负账单金额和非正还款状态都有记录。缺失率0也不代表每个字段含义明确。源数据已经是整理后的研究数据，无法证明它完整代表所有申请人。

第3步：把宽表拆成可练JOIN的表

clients：每个客户一行，只放ID和额度。monthly_history：每个客户每月一行，共180,000行，包含月份、还款状态、账单和支付。labels：每个客户一行，放次月标签和train/validation/test标识。

这些是同一真实源表的规范化拆分，不是来自银行的三个独立生产系统。没有生成新的行为记录。labels与特征表分开，是为了减少不小心把结果当特征的风险。

练习：客户总数应该保持30,000；一对六JOIN后180,000行是正常的，但是对额度直接SUM会被放大6倍。先聚合history到client_id再JOIN，就能保留一人一行。

第4步：自己写出特征SQL

real_project/feature.sql里有一个CTE h，先按客户聚合半年历史，再接额度。逐个理解：

特征如何计算业务直觉与限制
latest_status9月还款状态最新风险信号，非正编码作为类别
latest_util9月账单/授信额度账单相对额度的压力代理，不是精确剩余额度使用率
worst_delay6半年正向延迟状态最大值，非正设0历史最严重程度，非DPD天数
delay_months6半年pay_status>0的月份数反复延迟比孤立一次可能更重要
delay_months37–9月延迟月份数强调近期变化
bill_trend6(9月账单−4月账单)/额度比较增长方向，未解释中间路径
mean_paid_to_limit6半年平均支付/额度支付行为相对额度，不是收入比例
paid_trend6(近3月支付总和−前3月总和)/额度近期支付上升或下降，也可能受消费下降影响

MAX(CASE WHEN month='2005-09' THEN bill_amount END)为什么能取某月数值？每客户每月唯一，因此只有一个非空匹配值。若同月多条，该方法会悄悄取最大而非真正汇总，所以代码先验证唯一键。

SUM(CASE WHEN pay_status>0 THEN 1 ELSE 0 END)为什么是月数？因为聚合前已经是一人每月一行。同样公式放在多条事件日志中就成了事件次数。

第5步：用pandas独立复算SQL

代码用六列pay状态的gt(0).sum(axis=1)算每客户延迟月数。axis=1表示横向跨月份；axis=0则是纵向跨客户，业务含义完全不同。账单趋势直接用BILL_AMT1-BILL_AMT6，再除额度。

最后pd.testing.assert_frame_equal把两套实现对账。这个检查有意义是因为一套按长表SQL、一套按原始宽表pandas，运算路径不同。把同一个SQL执行两次比较不是独立验证。

第6步：先把数据分好再训练

按标签分层随机抽取18,000训练、6,000验证、6,000测试，种子42/43使结果可复现。分层保证各部分的违约比例近似一致。三个ID集合无交集。

重要：所有客户都处于同一历史窗口，所以是随机客户留出，不是时间外OOT。更严谨的生产验证需要其他月份/年份的数据。此处没有这样的数据，不能通过给随机样本加日期假装OOT。

第7步：基准与改进方案

基准：credit_limit、latest_util和类别型latest_status，逻辑回归C=1。改进：再加入半年频率、严重度和趋势，只在验证集从C=0.01/0.1/1中选AUC最高值。

ColumnTransformer将数值特征交给StandardScaler，当前状态交给OneHotEncoder；make_pipeline把预处理与模型连起来。StandardScaler只从训练集计算均值/标准差，避免验证测试数据泄露。OneHotEncoder将不同状态变为0/1列，避免假定-2、0等的业务距离等于数字距离。handle_unknown='ignore'允许未来出现未见类别时不报错，但仍应另行监控新类别。

LogisticRegression输出概率；predict_proba[:,1]取“违约1”那一列，不是客户ID。代码没有上复杂模型，目的是先把数据口径、基准和验证流程做扎实。

改进同时引入新特征和验证集正则选择，所以不能把全部提升只归因于时间特征。后续若要研究因果贡献，应做控制C一致的消融，并在新测试集上确认；本次不继续根据已见测试结果调参。

第8步：阈值怎么定

预设模拟复核容量约20%。各模型在验证集上取预测分数80%分位数作为阈值，固定后用于测试。相等分数都标记，因此验证集也未必恰好20%，测试集覆盖更不会被强行设成20%。

def three_sum(nums):
    a=sorted(nums)                     # sorted copy, keep input unchanged
    out=[]
    for i in range(len(a)-2):
        if i>0 and a[i]==a[i-1]:continue
        if a[i]>0:break                # remaining numbers cannot sum to zero
        left,right=i+1,len(a)-1
        while left<right:
            total=a[i]+a[left]+a[right]
            if total<0:left+=1
            elif total>0:right-=1
            else:
                out.append([a[i],a[left],a[right]])
                left+=1;right-=1
                while left<right and a[left]==a[left-1]:left+=1
                while left<right and a[right]==a[right+1]:right-=1
    return out

def quick_sort(nums):
    # Pedagogical three-way version, not in-place. Choose a random pivot in production
    # if adversarial inputs matter; Python's built-in sorted is usually preferable.
    if len(nums)<=1:return list(nums)
    pivot=nums[len(nums)//2]
    less=[x for x in nums if x<pivot]
    equal=[x for x in nums if x==pivot]
    greater=[x for x in nums if x>pivot]
    return quick_sort(less)+equal+quick_sort(greater)

def max_below(n,digits):
    """Largest nonnegative integer < n, unlimited digit reuse, no leading zeros.
    Zero is allowed only if 0 is in digits. None means no feasible answer.
    At most 10 allowed digits. Greedy equal-prefix walk with backtracking.
    """
    if not isinstance(n,int):raise TypeError('n must be an integer')
    if any(not isinstance(d,int) or not 0<=d<=9 for d in digits):raise ValueError('digits must be 0..9')
    allowed=sorted(set(digits),reverse=True)
    if n<=0 or not allowed:return None
    target=[int(x) for x in str(n)];L=len(target)
    def search(pos,prefix):
        if pos==L:return None           # identical n is not strictly smaller
        for d in allowed:
            if pos==0 and L>1 and d==0:continue
            if d>target[pos]:continue
            if d<target[pos]:
                return prefix+[d]+[allowed[0]]*(L-pos-1)
            result=search(pos+1,prefix+[d])
            if result is not None:return result
        return None
    out=search(0,[])
    if out is not None:return int(''.join(map(str,out)))
    for length in range(L-1,0,-1):
        first=next((d for d in allowed if d>0 or length==1),None)
        if first is not None:return int(str(first)+str(allowed[0])*(length-1))
    return None

old.ipynb SQL逐句解释

1. 内层从一个股票一个月份的表取交易时刻与成交量。

2. SUM(CASE WHEN BuyOrSell='S' THEN TradeVolume ELSE 0 END) OVER (...)：每笔卖成交贡献TradeVolume，其他笔贡献0；窗口使每条原始行带上当天截至当前时刻的累计卖量。买量同理。

3. PARTITION BY CAST(TradingTime AS DATE)：每天重新累计。如果TradingTime原字段只是TIME而非带日期的时间，这一假设就不成立，必须查数据类型；不把代码作者意图当事实。

4. ORDER BY TradingTime决定累计顺序。SQL Server在适用的有ORDER BY聚合窗口中省略frame时通常使用RANGE到当前值，因此相同时间戳的行会一起纳入；显式ROWS需要稳定唯一键。应说明想要“同一时刻全部成交”还是“逐笔先后”。

5. 外层先筛四个采样分钟，再按分钟GROUP BY。MAX(BuyVol)取该分钟最大累计量，仅在成交量非负、累计量单调时相当于分钟末值；负修正值会破坏假设。

6. SellVol != 0 AND BuyVol != 0筛的是累计量，非当前笔量；会剔除只有单边累计成交的采样点。

7. pandas groupby(date).diff()相邻采样累计值做差，得到相邻“实际保留下来的采样点”之间增量。首行缺差分，用当天累计量填补。采样点缺失时，下一段自动拉长。

8. 排序必须贯穿SQL输出、跨月拼接、分股票差分。源month列表乱序可能导致错误，稳妥做法是股票内按完整时间排序后再差分。

9. SELECT 1仅验证连接可执行简单查询，不能证明目标表权限、数据正确、吞吐或完整性。
